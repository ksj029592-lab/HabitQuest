- 시즌 기간·자기 순위·점수·실제 지급 이력은 기존 기능을 유지했다. 자동 정산과 새 보상 정책은 추가하지 않았다. 정산은 기존 운영 CLI 경계에 남아 있다.

## 반복 일정과 기록의 의미

- KST 날짜와 월요일 시작 주를 사용한다. 매일은 주 7일, 요일 지정은 선택 요일 수가 목표이며, 주 N회는 요일을 지정하지 않고 주 1~7개의 서로 다른 실천 날짜를 목표로 한다. 서로 모순되는 입력은 서버에서 거절한다.
- `UserHabit.id`가 영구 연결 키다. `scheduleHistory`는 적용 날짜를 가진 버전 배열이고 `DailyQuest.habitSnapshot`에는 생성 시 이름과 일정이 남는다. 이름 수정과 보관으로 완료 기록을 옮기거나 지우지 않는다.
- 새 습관은 오늘부터 적용한다. 기존 습관의 일반 일정/활성 변경은 다음 날, 주간 방식이 관련된 변경은 다음 월요일부터 적용한다. 같은 적용일의 예약 변경은 아직 적용 전인 버전만 교체한다. 과거 버전은 수정하지 않는다. 보관 시에는 내일부터 비활성인 이력을 추가하고 이후 생성에서는 즉시 제외한다.
- 일정 없는 날짜는 습관 연속 기록의 실패로 세지 않는다. 주간 연속 기록은 끝난 주만 평가하며, 도중에 만든 첫 부분 주는 연속 주 평가에서 제외한다. 일 단위와 주 단위 전환 시 연속 기록의 단위를 섞지 않는다.
- 새 주 N회 습관의 첫 부분 주에도 설정한 N이 표시된다. 목표를 남은 일수에 맞춰 자동 감산하지 않는다.
- 기존 출석·전체 스트릭·방지권 정책은 별개이며 변경하지 않았다. 습관별 연속 실천과 전체 출석 스트릭은 서로 다른 지표다.

## 생성과 비용

- 서버 DB에서 오늘 실천 가능한 활성 습관을 고른다. 주간 목표를 채웠거나 오늘 이미 완료한 습관은 제외한다. 최근 생성일이 오래된 습관부터 순환하며, 후보마다 퀘스트 하나씩 최대 3개를 만든다.
- 후보가 1~2개면 그 수만 생성하고, 0개면 추론 호출 없이 빈 목록과 습관 관리 안내를 제공한다. 기존 당일 퀘스트가 있으면 설정 변경이나 재접속으로 채우거나 초기화하지 않는다.
- 리롤도 같은 후보 정책을 사용하며 완료 슬롯을 유지한다. 후보가 없거나 생성/검증이 실패하면 기존 퀘스트와 티켓이 유지된다. 생성 중 습관이 바뀌면 저장을 중단한다.
- 모델에 설명·메모·반복 정책·최근 제목을 전달한다. 개수, 제목/설명 길이, 제목 중복, 허용 카테고리, 카테고리 중복을 검증한다. 난이도는 서버 선택값이고 XP/골드는 기존 범위로 정규화하며 포인트·상한·감산은 기존 서버 규칙을 사용한다.
- Foundry 장애를 로컬 예시로 숨기지 않는다. 기존 타임아웃·응답 크기·동시성·호출 제한을 유지하고, 동일 프로세스의 중복 생성·리롤·질문·동일 답변 제출은 진행 중 Promise를 공유한다. 실패 후에는 명시적으로 재시도할 수 있다. 분산 캐시는 추가하지 않았다.

## 승인 후 별도로 실행할 배포 순서

1. 이 개발 브랜치의 변경을 검토하고 배포 대상 커밋을 확정한다. master에 직접 push하지 않는다.
2. 현재 백업·PITR 시점과 실제 운영 행 수·스키마를 읽기 전용으로 확인하고, 별도 승인을 받는다. 테스트 fixture 파일은 절대 운영에서 실행하지 않는다.
3. 승인된 `backend/prisma/custom-habits-upgrade.sql`만 적용한다. 사용자별 최초 연결만 수행하므로 나중에 이름을 수정한 후 재실행해도 습관을 중복 생성하지 않는다. 잠금 3초·문장 60초 제한을 넘으면 트랜잭션이 실패하고 되돌아간다. 대량 데이터에서는 사전 복제 DB로 소요 시간을 확인한다.
4. 기존 인프라에 API → 준비 상태 → 웹 순서로 배포한다. 현재 루트 `azd up`의 프로비저닝 경로를 임의 실행하지 않는다. 기존 배포 파이프라인/이전에 검토한 이미지 갱신 경로를 사용한다.
5. 같은 운영 URL에서 버전 일치, 준비 리비전·트래픽, 페르소나 목록을 읽기 전용으로 확인한다. 쓰기 동작과 유료 추론은 별도 허용 범위에서 검증한다.
6. 앱 롤백 시 이전 이미지로 복원한다. 추가 테이블·컬럼과 연결 메타데이터를 삭제하지 않는다. 새 습관 메모/일정은 구버전 UI에서 편집되지 않지만 이전 게임 기록·세션·보상은 유지된다.

## 남은 제약과 추천 순서

- 이름과 실제 카테고리가 일치하지 않는 레거시 기록은 예전 카테고리 이름의 보관 습관으로 남긴다. 사용자의 원래 의도를 추측해 다른 습관으로 옮기지 않는다.
- 습관 8개와 하루 3개 퀘스트 제한을 함께 유지한다. 동시에 실천할 습관이 많으면 순환 선정되므로 모든 매일 습관에 매일 퀘스트가 배정되지는 않는다. 이후 우선순위나 목표 과다 안내를 검토한다.
- 동일 프로세스의 중복 AI 호출은 합치지만 여러 리비전/복제본 간 추론 중복까지 막는 분산 잠금은 없다. DB 지급·티켓·생성 중복 보호는 기존 트랜잭션으로 유지된다.
- 습관별 통계는 현재 해당 사용자의 전체 연결 기록을 읽는다. 장기간 사용량이 커지면 페이지 단위 상세와 DB 집계로 전환한다.
- 실환경 유료 추론 품질, PostgreSQL 복원 리허설, 신규 기능의 실제 운영 배포는 아직 검증하지 않았다. Vite 설정의 기존 CommonJS/ESM 사전 경고도 남아 있으나 빌드는 통과한다.
- 다음 단계는 승인된 스키마·릴리스 검토, 습관 우선순위/목표 과다 안내, 완료 요약의 기간별 확장, 시즌 종료 결과 화면 강화 순서가 적절하다.

## 후속 UX 점검
- 서버의 동일 후보 계산으로 전체(보관 포함), 비보관, 활성, 오늘 후보 수와 최대 3개를 제공한다. 이미 완료한 오늘 습관과 주간 목표 달성 습관은 후보에서 제외된다. 기존 당일 퀘스트는 재배정하지 않는다.
- 관리 화면에서 보관 기록을 열어 볼 수 있으며 보관 항목의 수정/보관 동작은 숨긴다. 목록 로딩 중 새 습관 추가를 막는다.
- 우선순위는 이번에 구현하지 않는다. 영구 저장과 API 계약 변경이 필요하다. 다음에는 높음/보통/낮음 저장 필드와 함께 대기일 우선, 같은 대기일에 우선순위를 적용하는 방식을 권장한다. 미배정 대기일은 기존 생성 기록에서 계산하며 낮은 우선순위도 대기일이 늘면 우선 배정한다. 동률·모든 항목 높음·장기 저순위·요일/주간 목표·리롤의 공정성 테스트가 필요하다.
- 배포 체크리스트: 백업/운영 행 수 확인 → 별도 SQL 승인 → 추가 스키마 적용 → API 및 구웹 호환 확인 → 웹 배포 → 동일 URL/버전/준비 상태 확인. 실패하면 웹부터 이전 이미지로 복원하고 API를 복원하며 추가 컬럼은 삭제하지 않는다. 실제 운영 SQL/이미지 변경/복원 리허설은 실행하지 않았다.

## 시즌 결과 UI 후속
- 기존 테이블만 읽는 GET /ranking/results를 추가했다. 최근 12개 저장 시즌의 기간·포인트·양수 참여자 순위·실제 지급 로그를 반환한다. 쓰기/정산/새 스키마는 없다.
- 진행 중/종료 후 정산 대기/정산 완료 지급됨/정산 완료 지급 기록 없음/미참여를 구분한다. 지급 로그가 없으면 지급 대상이 아니라고 단정하지 않는다. 최종 순위는 보관된 포인트 로그에서 재구성하며 별도 정산 스냅샷은 아니다.
- 이전 시즌 선택과 현재 랭킹 이동을 지원한다. 일일 요약·습관 관리·보상 정책은 변경하지 않았다. 구 API에는 결과 경로가 없으므로 다음 배포는 기존 습관 SQL 승인·선행 적용 후 API → 웹 순서를 유지한다.


## 일일 퀘스트 수 변경 (2026-11-08)

오늘 실천 가능한 습관이 하나 이상이면 습관 수와 관계없이 퀘스트 3개를 생성합니다. 습관이 적으면 같은 습관에 서로 다른 과제를 배정합니다. 리롤은 완료 슬롯을 유지하고 미완료 슬롯 수만큼 생성합니다. 후보가 없으면 AI를 호출하지 않으며 이미 생성된 오늘 퀘스트는 유지합니다. 기존 난이도별 보상, 동일 카테고리 세 번째 완료 감산 및 일일 상한은 유지합니다.

기존 오늘 퀘스트가 1~2개인 경우에도 다음 접속 시 부족한 슬롯만 추가합니다. 기존 퀘스트 ID·완료 기록·보상을 유지하며 사용자 잠금 안에서 슬롯을 재확인합니다. 추가 시 스트릭·방지권 처리를 반복하지 않습니다.
